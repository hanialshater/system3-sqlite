- **finding** (belief 0.75): Single-table row order when indexes exist. If an index satisfies the ORDER BY (a column prefix including the implicit trailing rowid, with all directions equal or all flipped), SQLite scans it, and a flipped match is a reverse scan that also reverses rowid ties. The same happens for GROUP BY when the index prefix equals the set of GROUP BY columns; groups then come out in index order. A range-only WHERE index loses to such an index; an equality WHERE index wins. A GROUP BY containing the rowid with no such index scans the table. A lone min() or max() on an indexed column reads from the index end, so among ties the row with the largest rowid wins for max on an ASC index or min on a DESC index.
  - evidence: index fuzz (fuzz.py --idx): single-table mismatches went to 0. Probe files oi.sql, mm.sql and g1.sql matched, except DISTINCT over two indexes. Commit before land 16a5170. · source: B12-continued O m-engine
- **practice** (belief 0.7): Row order without ORDER BY mostly doesn't matter for this corpus, but a small planner subset is cheap and safe:
- Covering-index full scan: pick the smallest estimated index-row width; it must be narrower than the table row.
- Single-index search when a top-level WHERE term on an index's first column has a matching collation: equality beats range, then covering, then smaller, then most recent. Scanning the whole index in index order and still applying WHERE gives the same order.
- A rowid term keeps rowid order.
- A partial index implied by the WHERE is scanned.
Use EXPLAIN QUERY PLAN in sqlrun as the oracle.
  - evidence: On the extended fuzzer, row-order-only mismatches dropped 54 -> 0-2, with no regressions on the corpus (still 100%). · source: B11 V V
- **finding** (belief 0.7): Join row order without ORDER BY matters often. A cheap two-table model reproduces most of SQLite's choices. The inner loop is the table searchable by an equality join term (a real index or rowid beats an automatic index, which beats nothing); on a tie keep FROM order. Scan the outer table through a covering index when one is narrower than the table. For inner lookups, keep rowid order within equal keys.
  - evidence: On a join/affinity fuzzer: 263/1945 statements were order-only mismatches; 170 after the loop-order rule; 51 after outer covering scans; a second seed gave 57/1949. There were 0 value mismatches throughout and no corpus regressions. · source: B12 V V
- **dead-end** (belief 0.65): Do not emulate SQLite's cost-based join reordering for this corpus. - **finding** (belief 0.85): In the driver, a statement that returns columns prints no `changes:` line. ## value-semantics

- **finding** (belief 0.85): Several SQLite behaviours are only discoverable by asking the oracle, and are cheap to check with one-line SELECTs: sum/total/avg use exact int accumulation with Kahan-Babuska on the first real, and ints >= 2^52 are split into big and small-remainder (mod 16384) parts when stepped into the double accumulator; 'integer overflow' only if overflow happened and no real ever appeared; text '1e3' in sum is numeric_type REAL (not integerized); bit operators and % use the integer prefix of text (atoi) so '1e3' | 0 = 1 but '1e3' + 0 = 1000.0; % with any real operand yields a real; scalar min() keeps the LAST of equal values while max() and the aggregates keep the first; substr of an empty blob is NULL; unicode of a string starting with NUL is NULL; replace with empty pattern returns the input even if the third arg is NULL; round() always returns real; length/instr/substr/LIKE count UTF-8 chars and text is cut at the first NUL; printing in the driver also cuts text at NUL (fputs).

- **finding** (belief 0.85): Non-TEMP views and triggers resolve unqualified table names only in their own database (sqlite3FixSrcList). This applies to DML targets in trigger bodies too. ## constraints

- **finding** (belief 0.8): SQLite's INSERT check order: NOT NULL; then, only if the table has CHECKs, affinity + STRICT type check followed by CHECK; then the rowid/IPK uniqueness check; then the STRICT type check if not already done; then unique indexes, newest-created first. An upsert whose target is a unique index checks that index first and moves the IPK check after it. OR IGNORE and DO NOTHING skip on an IPK conflict before the type check, but cannot suppress the type error. The STRICT message names the value's class after affinity ('-9620.1' into INTEGER -> REAL).
  - evidence: Verified with sqlrun on scratch t1/t4/t5/t10/t12; commits 'constraint check order (IPK, type, unique; upsert target first)' and 'STRICT error names value class after affinity'. The dml family went 95.3% -> 100%. · source: B11 O m-architect
- **finding** (belief 0.8): In an upsert, excluded.* holds the raw VALUES value with no column affinity ('1e3' stays text, -0.0 stays real), unless the table has CHECK constraints, in which case affinity has been applied. A REAL column still reads integers back as reals (260 -> 260.0). Unqualified names in DO UPDATE SET refer to the target table, never to excluded.

- **finding** (belief 0.75): INSERT constraint check order:
- With CHECK constraints: NOT NULL, then STRICT type check + CHECK, then rowid conflict, then unique indexes (most recently created first; autoindexes of one CREATE TABLE in reverse declaration order).
- Without CHECKs: the type check moves after the rowid check.
- Upsert on the rowid skips the type check.
- excluded.* holds pre-affinity values unless the table has CHECKs.
- UPDATE that moves the rowid: CHECK, then rowid, then type.
- A failed DML statement resets changes() to 0; DDL repeats the previous changes() value.

## architecture

- **practice** (belief 0.8): Representing TEXT as a Java String whose chars are the raw UTF-8 bytes (latin1 byte-strings) was the right call: memcmp collation is plain compareTo, invalid UTF-8 produced by blob||text survives output, and blobs are a record holding the same kind of string. Cost: every character-aware function (length, substr, instr, trim, LIKE/GLOB, unicode, char) must work on bytes via SQLite's Utf8Read semantics (continuation bytes 10xxxxxx are consumed greedily; invalid bytes map to themselves, not U+FFFD). I initially decoded to Unicode and had to redo trim/unicode/LIKE for raw bytes late.
  - evidence: ARCHITECTURE.md; commit 05c6712 (utf8-units); unicode(x'bac24a') = 186 in SQLite vs 65533 with a decoder. · source: B11 O m-values
- **practice** (belief 0.8): Keep the database as an immutable Clojure map held in one volatile per script. Statements read live rows through it, so triggers and subqueries see changes made mid-statement. Rollback of a statement, ROLLBACK and ROLLBACK TO are just restoring a snapshot. Keep index trees (persistent sorted-set-by over [key... rowid]) inside the table record, so they roll back for free too.
  - evidence: Savepoint/transaction/trigger probes all matched sqlrun. Index trees cut a 5000-row unique-insert plus self-join script from 22 s to about 1.5 s with no corpus change. · source: B12 V V
- **practice** (belief 0.75): Two cheap designs worked. Transactions and savepoints: keep the db as an immutable value and store snapshots in :tx, so rollback is just restoring a value. Attached databases: store their objects under prefixed keys ('aux.t1' with :db) and run a statement-qualification pass at exec entry that rewrites table references. With nothing attached the pass returns the statement unchanged, so it carries no risk for other scripts.
  - evidence: exec-tx matched the sqlrun probe on the first try; attach pass d91e201 0.7228 -> 0.7277 with no regressions · source: B12 O m-architect

## window-functions

- **finding** (belief 0.8): Row order and tie order with several windows follow SQLite's window rewrite (sqlite3WindowRewrite). Windows equal to the first window (same partition, order and normalized frame) are computed at the outer level. Every other window function moves into a nested sub-select, recursively, and so do ORDER BY copies of windowed result columns (referenced by number, alias or equal expression). The innermost level is computed first, and each level stable-sorts the rows coming from the level below by its own partition and order keys. Ranking functions get fixed frames before windows are compared: row_number and lag are ROWS UNBOUNDED PRECEDING..CURRENT ROW; rank, dense_rank and the default frame are RANGE UNBOUNDED PRECEDING..CURRENT ROW. A result column that the ORDER BY refers to displays the value of the ORDER BY copy (SQLITE_ECEL_OMITREF). Column references written differently (t.d vs d) and ASC NULLS FIRST vs plain ASC count as the same window.
  - evidence: Window fuzz with heavy ties against sqlrun: 25 mismatches of 1158 before, 3 of 1193 after. Probe files w7, w8, w9 and f3_15y all matched exactly. · source: B12 O m-engine
- **finding** (belief 0.8): sum, total and avg over a sliding frame (no EXCLUDE) use one accumulator per partition: rows enter through step and leave through an inverse step. Once a REAL or non-numeric text value has passed through the frame, every later sum in that partition is REAL (100.0, not 100). Frames with EXCLUDE recompute per row. Frame offset errors ('frame starting offset must be a non-negative integer' for ROWS/GROUPS, '... number' for RANGE) are raised at run time, after the header and only when rows exist. 'unsupported frame specification' and 'RANGE with offset PRECEDING/FOLLOWING requires one ORDER BY expression' are raised at prepare time.
  - evidence: fuzz case f4_17: SQLite printed 100.0|10.0|2.0 where recomputing each frame gave 100|10|2; fixed by implementing the inverse step for sum/total/avg. 'ROWS 1.5 PRECEDING ... WHERE 0' printed the header with no error. · source: B12 O m-engine
- **finding** (belief 0.8): Several windows in one SELECT follow SQLite's window rewrite. The outer level computes the windows equal to the first one (same partition, same order, same normalized frame); every other window function moves into a nested sub-select, recursively. ORDER BY copies of windowed result columns also move down, and the displayed column shows the copy's value (SQLITE_ECEL_OMITREF). The innermost level is computed first, and each level stable-sorts the rows coming from the level below. Ranking functions get fixed frames (row_number and lag ROWS, rank RANGE, and so on). sum/total/avg over a sliding frame use one accumulator with an inverse step, so once a non-integer value has passed through, later sums are REAL.
  - evidence: window fuzz with heavy ties: 25 -> 3 mismatches; probe files w7, w8, w9 and f3_15y matched; board post #24. · source: B12-continued O m-engine

## error-messages

- **finding** (belief 0.8): Wording of aggregate misuse errors:
- 'misuse of aggregate function f()' in UPDATE SET, UPDATE/DELETE WHERE, and the WHERE of a query without GROUP BY.

- **finding** (belief 0.8): Precedence of SELECT error messages:

## evaluation-semantics

- **finding** (belief 0.75): Value-context AND/OR evaluate both operands, so runtime errors like abs(-9223372036854775808) surface. Condition contexts short-circuit with two modes (sqlite3ExprIfTrue vs IfFalse): WHERE/CASE decide TRUE (NULL left stops AND); NOT and CHECK decide FALSE. Further rules:
- Parse-time folding: <non-NULL literal> IS [NOT] NULL becomes 0/1; X AND 0 becomes 0 unless either side contains a function.
- Codegen simplification: AND/OR with a 32-bit integer literal operand reduces to the other side's truth value.
- Constant top-level WHERE terms are evaluated before the scan (even on an empty table).
- A constant IN list of 3+ items is evaluated in full.
- rowid IN (uncorrelated subquery) runs the subquery before the scan.
  - evidence: Each was confirmed with sqlrun probes. The overflow-injected fuzz went from dozens of mismatches to about 1 per 80k statements. The rowid IN fix hits a real corpus template (SELECT id FROM t WHERE id IN (SELECT id FROM t1 WHERE ...)). · source: B11 V V

## text-encoding

- **practice** (belief 0.85): Keep text byte-exact: decode script bytes with a surrogate-escape scheme (invalid bytes -> U+DC80..DCFF) and re-encode on output. Then port the byte-level semantics:
- length counts lead bytes and stops at NUL.
- substr segments characters like SQLITE_SKIP_UTF8 and stops at NUL.
- instr and replace work on bytes (replace treats a pattern starting with NUL as empty).
- trim reads its charset up to the first NUL and matches byte sequences.
- quote stops at NUL.
- LIKE/GLOB decode characters like sqlite3Utf8Read (32-bit wrap, U+FFFD).
- NOCASE compare stops at NUL.
- BINARY compare uses raw bytes.
  - evidence: The reference outputs contain invalid UTF-8 (63 lines in the visible corpus). A dedicated invalid-UTF-8 fuzzer went from 81 mismatches in 4000 to 0 in 32,000 after these ports. · source: B11 V V

## constraints-dml

- **finding** (belief 0.85): SQLite's constraint check order, confirmed by experiment: NOT NULL (column order) -> CHECK -> rowid/PK conflict -> STRICT type check -> unique indexes. CREATE INDEX on a missing table says 'no such table: main.t' (all other statements omit 'main.'). The last of several DEFAULT or COLLATE clauses on a column wins.

## driver-output

- **finding** (belief 0.85): Rules for when the driver prints 'changes: N' or an error. (1) BEGIN [DEFERRED], COMMIT, ROLLBACK, SAVEPOINT, RELEASE, ATTACH, DETACH, and CREATE/DROP TRIGGER IF [NOT] EXISTS no-ops print nothing. ## schema-text

- **finding** (belief 0.8): sqlite_master stores SQL as follows. Tables: 'CREATE TABLE ' plus text from the name token to ')' or the last table option. Indexes: up to the ';', keeping trailing spaces and comments. Views: up to the ';' with trailing whitespace trimmed. Triggers: through END. ## driver
