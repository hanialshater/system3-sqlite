# Benchmark 13: the org at scale, with fallible agents, toward 100% of SQLite's own tests

owner: vp-meta · date: 2026-10-25 · status: **design; predictions committed before any run** · founder, 2026-10-25:
"our purpose was org is scalable and allows for fallible agents, going to 100% is good idea"; "Approval for B13, about
$500. -> approved"

## The question

Does the autonomous org (B11/B12's design) **scale** (more members, more throughput) and **tolerate fallible
agents** (a careless member, a crashed member) without main getting worse, on the way to 100% of SQLite's own tests?

## The setup

- **Task, material, judge, rules:** as B12 (SQLite 3.53.4's own Tcl suite replayed through the driver; 480 hidden test
  files; the score is the mean per test file; byte-exact; Clojure only).
- **Start:** B12's org main after the continuation (88.50% hidden, 92.69% visible).
- **On-boarding:** the knowledge base as it stands (158 entries from B11 and B12), in `spec/KNOWLEDGE.md`.
- **Budget:** $500 for the org; no wall-clock cap below 10 hours; **stops** when main gains nothing for 60 minutes
  (after the first hour) or reaches 100% visible.
- **Eight members** (one continuous session each; sync, land, notes, the board, claims, idle; the shared budget):

| Member | Model | Starting role |
|---|---|---|
| m-architect | Opus | the big picture and the interfaces; coordinates; also builds |
| m-engine | Opus | query execution: SELECT, joins, subqueries, aggregation, windows, CTEs |
| m-language | Sonnet | the SQL language: parser, error messages, DDL, constraints, triggers, DML |
| m-values | Sonnet | values and functions: affinity, comparison, arithmetic, formatting, date/time, JSON |
| m-schema | Sonnet | the schema and its commands: ALTER TABLE, PRAGMAs, ATTACH, VACUUM, sqlite_schema |
| m-planner | Sonnet | behaviour the query planner makes visible: index choice and scan order, rows' order without ORDER BY, ANALYZE |
| m-sweeper | Sonnet | the weakest test files, whatever their area: find what fails most and fix it or hand it to its area's member |
| m-hasty | Haiku | **the fallible member**: told to move fast, land as often as it can, and not spend long checking |

- **A crash:** at 45 active minutes, m-engine's session is killed mid-turn; it is resumed 20 minutes later (its tree as
  it was left, its session context restored).
- **Measured:** main's score over time; lands per member and their gains; refused lands (whose); whether main ever
  fell; what the org did about the crash and the hasty member (notes, reviews, reverts); cost per point; the hidden
  score at the end.

## Harness deviations (logged during the run)

- **10:50:45, a false plateau stop.** The plateau rule measured "minutes since the last gain" against the ledger rows
  as read before the start row was written. The last gain was therefore counted as happening at read time, and at
  minute 60 every member was stopped while main was still rising (0.9362 visible, last gain 10:43, 17 lands, $165
  spent). Fixed: the rule now uses the last gain's own time. Resumed at 10:51:59 with `--resume`: same sessions, same
  caps ($500, 600 minutes). Members were told once that the stop was the harness's fault. Downtime was 1 minute.
  m-engine's planned crash (10:35) and recovery (20 minutes down) were not affected. The "end" row at 10:50:45 is
  superseded by the run's last "end" row, which is the one final scoring reads.
- **Bearing on the predictions:** B13-9 (the org stops by its plateau rule before spending the $500) is judged only on
  the resumed run's end. The false stop is not evidence for it.
